## 2. Поднятые сервисы — и почему именно они

Сервисы запущены через Docker Compose. Все пять основных контейнеров работают и имеют статус healthy.

| Сервис                    | Роль в стеке                                                                | Почему именно он (а не альтернатива)                                                             |
| ------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| MinIO                     | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы)    | Можно работать с S3 локально, без облачного аккаунта. Данные сохраняются в Docker-томе.          |
| PostgreSQL                | БД, где Lakekeeper хранит метаданные каталога                               | Lakekeeper использует PostgreSQL для хранения своего состояния. При перезапуске оно сохраняется. |
| Lakekeeper                | Iceberg REST Catalog — каталог метаданных таблиц                            | Оба движка видят одни таблицы; отдельный Hive Metastore не нужен.                                |
| Trino                     | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Есть коннекторы TPC-H и Iceberg, всю работу можно сделать SQL-запросами.                         |
| Spark Thrift Server       | Второй SQL-движок с JDBC-доступом к тем же таблицам.                        | Через него проверил чтение тех же данных другим движком. Использовал режим local[4].             |
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold                                                   | Не поднимал: для SQL и просмотра результата использовал DBeaver.                                 |

Для SQL использовал DBeaver, отдельный BI-сервис не поднимал. Вспомогательные migrate и minio-init подготовили каталог и бакет, затем завершились с кодом 0.

## 3. Разбор запроса — какие данные нужны

Запрос находит топ-20 клиентов по выручке от возвращённых позиций за IV квартал 1993 года. Исходные данные — tpch.sf10, их копии — bench.bronze.

| Таблица TPC-H | Нужные колонки                                             | Что запрос с ними делает (фильтр / джойн / агрегат / вывод)            |
| ------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| customer      | custkey, name, nationkey, acctbal, address, phone, comment | Связь с заказами и страной, группировка и данные клиента в результате. |
| orders        | orderkey, custkey, orderdate                               | Связь с клиентом и позициями, отбор квартала по дате заказа.           |
| lineitem      | orderkey, returnflag, extendedprice, discount              | Отбор возвратов и расчёт выручки с учётом скидки.                      |
| nation        | nationkey, name                                            | Название страны клиента.                                               |

```sql
SELECT c.custkey, c.name,
       sum(l.extendedprice * (1 - l.discount)) AS revenue,
       c.acctbal, n.name AS nation, c.address, c.phone, c.comment
FROM bench.bronze.customer c
JOIN bench.bronze.orders o ON c.custkey = o.custkey
JOIN bench.bronze.lineitem l ON o.orderkey = l.orderkey
JOIN bench.bronze.nation n ON c.nationkey = n.nationkey
WHERE o.orderdate >= DATE '1993-10-01'
  AND o.orderdate < DATE '1994-01-01'
  AND l.returnflag = 'R'
GROUP BY c.custkey, c.name, c.acctbal, n.name, c.address, c.phone, c.comment
ORDER BY revenue DESC, c.custkey
LIMIT 20;
```

Период берётся по orderdate. Дополнительная сортировка по custkey задаёт порядок при одинаковой выручке.

## 5. Тесты производительности

Q10 запускался напрямую на Bronze sf10. Для GZIP созданы копии в bench.bronze_gzip, ZSTD остался в bench.bronze. Колонки, строки и партиционирование совпадают, в каждом наборе по 85 файлов. Оба кодека проверены в Parquet.

Каждый вариант сначала запустил один раз для прогрева, затем сделал по три замера, чередуя кодеки. Время считал между created и end в system.runtime.queries. Размер определял так же, как в разделе 4.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему)                                                                 |
| ---------------- | ------------- | ----------------- | ----------------------------------------------------------------------------------------------- |
| GZIP             | 3,785 с       | 2 086,578048      | Занимает на 2,32% меньше места, но Q10 выполняется дольше.                                      |
| ZSTD             | 3,176 с       | 2 136,148464      | Время запроса меньше на 16,09%. Оставил ZSTD, так как скорость важнее небольшой экономии места. |

Отдельные замеры: GZIP — 4,016; 3,747; 3,592 с; ZSTD — 3,254; 3,201; 3,073 с. В таблице указано среднее время.

GZIP занял на 2,32% меньше места, но запрос с ZSTD выполнялся быстрее на 16,09%. Поэтому оставил ZSTD. Топ-20 в обоих случаях совпал, при сравнении выручки учитывал погрешность double. Первый запуск не включал в среднее. Эти результаты получены на моём стенде по трём замерам.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос                                                                           | Твой ответ                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)?              | Данные хранятся в MinIO, а Trino и Spark работают с ними через общий каталог Lakekeeper. Хранилище и движки обработки можно менять и масштабировать отдельно. Для sf10 хватило бы и обычной БД, но в работе нужно было проверить возможности lakehouse: доступ из двух движков, изменение схемы и восстановление данных. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Для эксперимента создал silver.q10_evolution_demo из 10 клиентов. Добавил note VARCHAR, затем переименовал в quality_note: строки сохранились, новая колонка содержит NULL, путь и размер Parquet-файла не изменились. Поменялась только схема, файлы с данными не перезаписывались.                                     |
| Пример скрипта восстановления данных из снапшота (time travel)                   | До удаления было 10 строк, после удаления — 7, после восстановления снова стало 10. Это проверил в Trino и Spark. Колонка quality_note сохранилась. В командах указан ID снапшота этой таблицы; для повторения на новой таблице нужно взять её ID, пока снапшот ещё хранится в истории.                                  |

```sql
CREATE TABLE bench.silver.q10_evolution_demo WITH (format = 'PARQUET')
AS SELECT * FROM bench.silver.customer_nation ORDER BY custkey LIMIT 10;
ALTER TABLE bench.silver.q10_evolution_demo ADD COLUMN note VARCHAR;
ALTER TABLE bench.silver.q10_evolution_demo RENAME COLUMN note TO quality_note;

SELECT snapshot_id FROM bench.silver."q10_evolution_demo$snapshots"
ORDER BY committed_at DESC;
DELETE FROM bench.silver.q10_evolution_demo WHERE custkey IN (1, 2, 3);
SELECT count(*) FROM bench.silver.q10_evolution_demo; -- 7
SELECT count(*) FROM bench.silver.q10_evolution_demo
FOR VERSION AS OF 2492711815277284993; -- 10
ALTER TABLE bench.silver.q10_evolution_demo
EXECUTE rollback_to_snapshot(2492711815277284993);
SELECT count(*) FROM bench.silver.q10_evolution_demo; -- 10
```

### 6.2. Подключить инструмент к lakehouse

| Инструмент                                              | Почему выбрал именно его                                                                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apache Spark 3.5.3 + Iceberg 1.7.1, Spark Thrift Server | Подходит для SQL и пакетных преобразований, уже входит в стек. Проверил доступ к тем же таблицам, что и Trino. Использовал local[4], без отдельного кластера. |

Настройки spark-thrift находятся в compose.yaml, spark/Dockerfile и spark/start-thrift.sh. Внутри сети Docker Spark подключается к каталогу Lakekeeper на порту 8181 и к MinIO на порту 9000. Используется warehouse bench.

```powershell
docker compose up -d --build spark-thrift
docker compose exec --interactive=false -T spark-thrift /opt/spark/bin/beeline -u jdbc:hive2://localhost:10000/default -n report --silent=true --outputformat=tsv2 -e "SELECT count(*) FROM bench.bronze.customer;"
```

Проверка выполнена через Beeline. В DBeaver этому соответствует подключение Apache Spark, localhost:10000, база default. Сервер использует протокол HiveServer2.

```sql
SELECT 'customer' AS table_name, count(*) AS rows FROM bench.bronze.customer
UNION ALL SELECT 'orders', count(*) FROM bench.bronze.orders
UNION ALL SELECT 'lineitem', count(*) FROM bench.bronze.lineitem
UNION ALL SELECT 'nation', count(*) FROM bench.bronze.nation;

SELECT c.custkey, c.name, n.name AS nation
FROM bench.bronze.customer c
JOIN bench.bronze.nation n ON c.nationkey = n.nationkey
ORDER BY c.custkey LIMIT 5;
```

Spark получил те же количества строк, что и Trino: customer — 1 500 000, orders — 15 000 000, lineitem — 59 986 052, nation — 25. Для клиентов 1–5 соединение вернуло страны MOROCCO, JORDAN, ARGENTINA, EGYPT, CANADA. Spark также увидел 10 восстановленных строк демонстрационной таблицы и quality_note со значениями NULL.

## 7. Выводы

В работе прошёл путь от исходных таблиц до результата из 20 клиентов. На Silver оставил нужный квартал и подготовил соединения, а в Gold записал итог Q10. Для хранения выбрал Parquet с ZSTD: по замерам запрос выполнялся быстрее, хотя GZIP занимал чуть меньше места. На небольшой таблице проверил изменение схемы и восстановление удалённых строк. Spark прочитал те же данные, что и Trino, без повторной загрузки.
